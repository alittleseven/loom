## 二、本轮新发现

### P0 — 无

### P1 — 建议修复

- **P1-1 [loom/pipeline.py:126-176] halt 路径的 LLM 用量仍不入账。** `render_events`/`review_events` 只在成功 settle 时随事务写入 run-ledger；机检重试耗尽、评审阻断后重渲染仍失败这三条 `PipelineHalted` 路径上，已发生的 3 次渲染 + 2 次评审的 usage 全部丢弃——而失败章恰是全批次最贵的章。成本面板与 rerender_rate 熔断（依赖 render_call 事件）对 halt 章均失明。建议：halt 前用 `append_ledger_event`（core 已有该 API）补记累计 usage，或把 usage 载荷并入 `batch_breaker`/`pipeline_halt` 信号。
- **P1-2 [loom/edge/scribe.py:144/160] 金句收割仍直写已跟踪文件，收割后工作区变脏。** `harvest_candidates`/`confirm_golden` 经 `repo.write_file` 写 `文风/金句库/<scene>.md`（不在 gitignore 内），不落 settle 事务；收割与下一次 `loom next`/`batch run` 之间若无人工 git 提交，settle 必被"工作区不干净"拒绝，且 loom 无兜底提交命令。建议：两次写入改走 settle 事务（`actor="scribe"` 在矩阵内本有 文风/ 写权），与"所有产物写入过所有权矩阵"的新红线保持同一强制路径。

### P2 — 可选优化

- **P2-1 [loom/staging.py:131-134] `fulfillment_missed` 未按 resume offset 切片。** `WINDOW_SIGNAL_TYPES` 声明了它、`_signal_offsets` 也统计了它，但 `compute_breakers` 读它时不做 offset 过滤——resume 后旧章的 missed 若仍落在"最近 10 章 settle"窗口内会被计入。按章滚动窗口的口径这可以说得通（missed 是章级状态而非累计噪声），但与窗口重置的注释意图不一致，建议二选一：补 offset，或在注释里写明有意豁免。**待确认设计意图。**
- **P2-2 [loom/core/prep/prep.py:95-101] core 反向依赖包根工具模块。** `_book_map` 现在 `from loom.enhance import book_map_full`（函数内延迟导入避免循环），形成 `core/ → loom.enhance → core/*` 的依赖方向。建议把 `book_map_full`/`build_l0_skeleton` 下沉进 `core/prep/`，enhance 保留 CLI 编排。
- **P2-3 [loom/core/checks/checks.py:385-390] gate5 的 waiver.target 依赖 extra=allow 的 model_extra。** Waiver 是 P0 冻结 schema，`target` 目前是规范外扩展字段；spec v0.2 演进时应转正为声明字段，否则该消费点会一直游离在 schema 校验之外（且 `list(target)` 对非 str/list 类型会 TypeError，建议加类型守卫）。
- **P2-4 [loom/cli.py] 异常路径裸 traceback。** `cmd_next`/`cmd_review` 等对 `PipelineHalted`/`PlanRejected`/`ProviderError` 无捕获，用户看到的是 Python traceback 而非"第 N 章机检耗尽，工作区已保留"式的可读结论（信息其实都在异常对象里）。
