# 织机 Loom 架构与功能逻辑审阅报告

- 日期：2026-08-29
- 审阅对象：`projects/loom` @ HEAD `e708fbb`（源码约 4.2k 行 + tests 22 个文件 / 131 项测试）
- 审阅方式：全量通读 `loom/` 源码与测试、对照 v3.0 基线方案与 loom-1 规范、实跑 pytest
- 备注：审阅进行期间并行会话提交了 `e708fbb`（机检消费题材毒点），本报告基于该版本；审阅开始时 `test_poison_points_act_as_banned_words` 曾红（旧 `model_extra` 读法），随该提交转绿，全套测试复跑通过。

## 一、总体结论

**架构合格，骨架优秀；问题集中在"记账与熔断"这条观测链路上。**

三层架构（core 零 LLM / edge 全 LLM / evolve 离线）在代码中执行得很干净：`core/` 无一处 provider 调用，`edge/` 全部模型调用收敛在 LLMProvider 双方法协议后，`evolve/` 只读 signals。settle 的 git plumbing 原子事务（stage_blob → commit_tree → move_ref → worktree_sync + 五个故障注入点 + 幂等 recover + 哈希防串稿 + 只增不改）是全项目最扎实的部分，配得上"文件即真相"的设计承诺。

但七项熔断中实际只有三项有效、scribe 成本系统性漏记、resume 后熔断窗口错位——观测链路的失真不会让书写错，却会让"批次自动运行"这一核心卖点在关键时刻瞎掉。建议在进入下一 Phase 前优先修复第三节 A/B/C 三项。

## 二、架构评价（对照 v3.0 基线的亮点）

1. **双端口隔离做实**：`RepoPort`（ports.py）承载全部环境操作并内置五个故障注入点；`InMemoryRepoPort` 镜像 settle 语义并有同语义测试（test_settle.py::test_inmemory_port_same_semantics）。`LLMProvider` 六类单发、无 agentic 循环，transport 可注入 + cassette 录制回放，CI 无 Key 可跑。
2. **确定性贯彻**：prep 编译器输出只依赖书仓源文件（无时间戳），pack 字节一致有快照验收；300 章压测 pack 恒定（±20%）落地（enhance.pack_constant_check）。
3. **fail-closed 落地较全**：settle 拒脏工作区、哈希防串稿、只增不改须显式 retcon(N)、机检/评审重试耗尽即 PipelineHalted、规划 3 次未过门即 PlanRejected。
4. **防纸面功能机制**：配置-实现一致性检查（consumption.py）+ doctor 的 book.yaml 未知字段报错，是少见的自我约束设计。
5. **测试策略兑现**：settle 故障注入矩阵、长路径、cassette、消费点一致性均在；131 项测试全绿。

## 三、功能逻辑缺陷（按严重度）

### A.【高】scribe 成本漏记账——`chapter=None` 吞掉 ledger_events

`edge/scribe.py:103` 的 `scribe_commit` 以 `chapter=None` 调 settle，而 `core/settle/transaction.py:97` 仅在 `plan.chapter is not None` 时才把 `ledger_events` 写入 run-ledger。结果：**每章 2 次 scribe LLM 调用的 usage 永远进不了审计链**，`cost_report`/`cost_dashboard`/`loom ledger` 系统性低估约 1/3 的真实成本。`build_vol_summary`（scribe.py:183-187）同样中招。
建议：ledger_events 无条件写入（与 chapter 解耦），或 scribe 传 `chapter=chapter`。

### B.【高】resume 后熔断全瞎——信号窗口重置的下标跨类型错位

`staging.py:246-248` 把 `signal_window_reset` 算成 **5 类 signals 条数之和**，而 `compute_breakers` 把它当作**单类型列表**的下标用（`read_signals(repo, "gate_block")[since_signal:]`，staging.py:84、108）。resume 后新信号的实际下标必然小于该跨类总和，于是 gate_block / plan_deviation 类熔断指标在对应类型列表长度追平跨类总和之前**恒为空**——"防旧拦截连环放大"的机制顺手把新信号也屏蔽了。
建议：按类型分别记录 offset（如 `{"gate_block": n1, "plan_deviation": n2, ...}`）。

### C.【高】七项熔断中两项结构性恒零

- `missed_rate` 硬编码 0.0（staging.py:112），注释称"P1a 已埋 gate_block"但并无产出源——履约熔断永不触发。
- `rerender_rate`：`render_call` 事件只在 settle 时每章记一条（pipeline.py:174，且只记最后一次渲染），`render_counts == 章数` 恒成立，比率恒 0。重渲染次数其实已记在批次状态 `render_stats` 里，熔断没有消费它。
- 净效果：`DEFAULT_BREAKERS` 五条中只有 `check_block_rate`、`leak_hit`、`rhythm_debt` 有效。

### D.【中】重渲染 attempt 的 token 用量被丢弃

`run_chapter` 的机检重试循环中，每次 `render_chapter` 的 usage 只有**最后一次**随 settle 入账（pipeline.py:174-175），前几次 attempt 的消耗凭空消失。与 A 叠加后，成本电表对"模型烧了多少钱"的回答明显偏低。

### E.【中】章纲卡 touch 不存在的条目 id 被静默跳过

`_entry_ops`（pipeline.py:83-86）对 `entries.get(eid) is None` 直接 `continue`：不报 issue、不阻断。`check_entry_form` 只查 `manuscript.entry_changes`，而后者恰是预过滤后的产物——被绕过。部分承诺静默丢失，仅靠 `plan_deviation` signal 事后可观测，与 fail-closed 红线精神不符。
建议：`run_checks` 对 `card.touches` 增加存在性 block（或在 `_entry_ops` 直接拒绝）。

### F.【中】gate5 豁免粒度：一条豁免豁免全部超期条目

`run_plan_gates`（checks.py:378-382）中 `waivers = {w.reason ...}`，判定条件 `if eid not in covered and not waivers`——任何一条计划级豁免会让**所有**超期条目免于"无兑付安排"拦截，豁免未绑定具体条目。

### G.【中】批次异常路径与锁语义（对照"批次运行持锁"红线）

- `arm_batch`（staging.py:63-77）注释称"持写锁进入 ARMED"，实际只查不取；写锁仅在每次 settle 的毫秒级窗口持有，批次运行期间作者/其他进程可自由写工作区。
- 后果链：作者中途改动已跟踪文件 → 下一次 settle 的 dirty check 拒绝（且检查发生在 acquire 锁之前，transaction.py:67-69，存在 TOCTOU 小窗口）→ `SettleRejected` 不在 `run_batch` 的捕获范围（只捕 `PipelineHalted`，staging.py:172）→ 裸 traceback、批次状态卡在 RUNNING，而 `resume_batch` 拒绝 RUNNING 状态——只能靠重跑 `batch run`（靠 done 列表幂等续）。
- 建议：arm/run 前置 dirty+锁预检；`run_batch` 捕获 `SettleRejected`/`RepoBusy` 转入 HALTED 并记录原因；要么 arm 真正持锁，要么修正注释与 AGENTS.md 红线表述。

### H.【低】缝协议版本嗅探无生产调用点

`core/seam.py::assert_seam` 只有测试调用；决策卡写入（pipeline.py:51-67）自定义 `SEAM_VERSION = "1"`，与 `core/seam.py` 形成双源。core 读取工作区文件时实际从不校验 seam_version——"版本嗅探、不匹配显式降级"目前是纸面能力。

### I.【低】性能与实现细节

- `ledger._append` 全文件读-重写（非 O_APPEND），signals 高频追加下 O(n²)；gate_block 等信号在无锁状态下写入（依赖单写者假设）。
- `load_entries` 在 pipeline/prep/reviewers/checks 每章重复全量读盘；`check_timeline` 每次机检两遍扫时间线目录。300 章规模是 I/O 放大而非正确性问题。
- `check_no_hook` 词表含"？""！""死"（checks.py:32）——任何问号结尾即过，无钩检测近似空转（可接受为 P1a 形态，宜注明）。
- ownership 矩阵对未列路径对 `settle/author` 全开（ownership.py:42-43），settle 理论上可写 book.yaml。
- prep 的 book map 只挂"最早卷号"（prep.py:102 break）；完整版 `enhance.book_map_full` 已写好但未接入 `compile_pack`。

## 四、架构/文档偏差（代码与基线、AGENTS.md 不一致处）

1. **目录结构漂移**：staging/pipeline/planning/enhance 在包根（`loom/staging.py` 等）而非 AGENTS.md 规划的 `core/staging/` 等；edge 的 renderer/reviewers/scribe 是单文件而非子包。功能等价，但 AGENTS.md 目录说明已失真。
2. **命令面缺口**：AGENTS.md 规划的 `review`/`memory` 命令未实现；金句收割/确认（harvest_candidates/confirm_golden）、卷摘要（build_vol_summary）、P5 的 L0 骨架/book_map_full/synth_book/pack_constant_check 均无 CLI 入口（仅测试可达）——功能存在但不可达。
3. **evolve/migrate/synth 绕过所有权矩阵**：bench、migrate、synth_book 直接 `port.write_text`/`commit_tree`，矩阵的强制点只有 `BookRepo.write_file` 与 settle FileOp——"所有写入过矩阵"实际不成立。
4. **AGENTS.md 声称的"WinError 5 自动重试"未实现**：`GitRepoPort.write_text` 的 `os.replace` 无任何重试逻辑。

## 五、修复优先级建议

1. **立即**（一行级修复，收益最大）：A（ledger_events 门控）、B（窗口 offset 按类型）、C-rerender（从 `render_stats` 或逐 attempt 埋点取数）。
2. **下一批次前**：D（attempt usage 累加）、E（touch 存在性 block）、G（批次异常捕获 + 预检）、C-missed（把 `check_fulfillment` 的 missed 埋成信号）。
3. **文档对齐**：第四节 1/2/4（改 AGENTS.md 或补实现，二选一，消除"纸面功能"）。
4. **择机**：F、H、I 各项。
